## 1. 1.0.0の考え方

1.0.0はSemVer上「公開APIを壊さない約束」になる。したがって1.0前の作業の中心は機能追加ではなく、**後から変えると破壊的変更になるものを決め切ること**。追加だけで済むもの（ボード、USBなど）は1.xへ回せる。

## 2. 1.0前に決めるべきこと（後から直せない）

| # | 論点 | 現状 | 選択肢 |
|---|---|---|---|
| 2-1 | インスタンス名の意味がボードで違う | `Wire1`はA153/N947ではI3C経由、A156ではMikroBusのI2C。MikroBusのI2CはN947では`Wire2`。`Serial2`はA156だけ | (a) 現状のまま固定して文書で明示 (b) `WireMB`のようなボード非依存の別名を足す (c) 名前を付け替える（破壊的。やるなら1.0前のみ） |

## 3. 1.0前に潰したい弱点

- **LinkServer依存**: A153は26.9.130単独だと書き込めず、旧版（26.6.137など）の併存が必要。旧版はNXPのページに載っていない。初めてのユーザーが最初に踏む場所なので、根本対処か、NXPへの報告と回避の自動化のどちらかが要る
- **N947の`Wire2`がターゲットとして応答しない**: 原因不明のまま。解決するか、既知の制限として確定させる（A156の同じLPI2C3は応答する、という差が手がかり）
- **ネットワーク基底クラスが無い**: `Client`/`Server`/`UDP`/`IPAddress`。ヘッダの追加で済み、公式`Ethernet`ライブラリなどがコンパイルできるようになる
- **サードパーティライブラリの回帰**: 定番ライブラリ（Adafruit系など）をCIのコンパイル対象に入れ、「互換」の根拠にする。対象の選定が先

## 4. ボード追加の扱い

### 4-1. 方針案
- **C444**: 1.0の必須条件にしない。追加自体は非破壊なので1.xでよい。ただし1.0前に**「ビルドが通るだけ」のスパイク**を一度やり、M0+や別系統IPのせいで公開側（§2）の変更が要らないことだけ確認する
- **USB**: 1.xの追加機能

### 4-2. C444を入れる意味
- RAM 32KBでArduinoCore-zephyrでは載らない領域。ネイティブコアの存在意義が最も出る
- MCXで唯一のCortex-M0+（ARMv6-M）。コアに紛れたM33前提の実装が出る
- Kinetis KL系の旧世代IP（`fsl_i2c`、`fsl_spi`、TPM、ADC16、MCG-Lite）。抽象層が特定IPに依存していないことの検証になる
- A/N/Cが揃うことによるラインナップ上の説得力
- セグメントLCDは入門デモの題材になる
- 割り引く点: I3Cが無い、フラッシュ256KB/RAM 32KBで今後の拡張に制約、工数が大きい

### 4-3. r01libのC444対応状況（2026-08-11時点のコミット）

| クラス | 状況 |
|---|---|
| GPIO（`io`） | 対応。Alt番号が1つずれる件（Alt1=GPIO）は吸収済み |
| Serial | 対応。LPUART0（USBTX/RX = D1/D0）とLPUART1（MB_TX/RX）、割り込み駆動 |
| I2C | 対応（`fsl_i2c`）。I2C1固定。D18/D19（Alt6）またはA4/A5（Alt2） |
| SPI | 対応（`fsl_spi`）。SPI1固定 |
| InterruptIn | 対応。PORTA/C/Dのみ（ハード制約） |
| Ticker | 未対応。UTICKが無く、クラスごと`#ifndef`で除外 |
| AnalogIn / PwmOut | 未対応（A153限定にガード） |
| I3C | 非対応（ハードに無い） |

補足:
- `PORT_SetPinOpenDrain`相当はC444では空実装。GPIOのオープンドレイン出力は使えない
- `wait()`が`double`演算。FPUの無いM0+ではソフトフロートになる（コードサイズと短い待ち時間の精度）

### 4-4. C444の工数
- `CLAUDE.md`の「A156の4〜6倍」が妥当。コアはアナログ系を自前実装しているので、ADC16/TPMによる`analogRead`/`analogWrite`/`analogWriteFrequency`/`tone`の新規実装はC444固有の工数になる
- GPIO/Serial/Wire/SPI/`attachInterrupt`だけならr01libがそのまま使え、差分ポート＋M0+対応に近い
- C444固有で残るもの: M0+のコンパイルフラグ・スタートアップ・リンカスクリプト、Ticker相当（LPTMRかPITで代替）、アナログ系のバックエンド、RAM 32KBに合わせたバッファ既定値、ピン割り込みのポート制約の扱い

## 5. A4/A5でI²Cを使えるようにする

### 5-1. 対象ボード（同梱r01libの`i2c.cpp`のピン判定から。N236はZephyrの`MCXN236VDF-pinctrl.h`から）

| ボード | A4/A5のI²C | D18/D19との関係 |
|---|---|---|
| A156 | LPI2C1（Alt2、P1_12/P1_13） | 別ペリフェラル（`Wire`はLPI2C0）。同時に使える |
| C444 | I2C1（Alt2） | 同じI2C1（D18/D19はAlt6）。どちらか一方 |
| N236 | LPI2C2（Alt2、P4_12=`FC2_P0`、P4_13=`FC2_P1`） | `Wire1`（MB_SDA/MB_SCL、P4_0/P4_1）と同じLPI2C2。どちらか一方。FC2は`Serial1`とも共有。`0.9.0-dev`の`i2c.cpp`はA4/A5を受け付けず`panic`で止まる |
| A153 | 無し | A4/A5（P3_31/P3_30）はr01libの対応表に無い |
| N947 | 無し | 同上（P0_15/P0_23） |

### 5-2. 入口の案
1. **`TwoWire`をスケッチ側で作る**: `TwoWire WireA( A4, A5 );`。コンストラクタは公開済みで、r01libもA156のA4/A5を受け付ける。A156では今でも動く可能性がある（**未確認**: Arduino層の割り込みハンドラ、ターゲットモード、タイムアウトがLPI2C1で通るか）。正式サポートとして文書とテストを足す
2. **`Wire.setPins( sda, scl )`を足す**: A4/A5にI²Cが出ている旧UNO向けシールドを救うにはこちらが必要（ライブラリは`Wire`を決め打ちで使う）。`begin()`の前に呼ぶ。非対応の組み合わせは既存の流儀どおり`panic`で対応ピンを示す。名前はESP32系の`setPins`か、STM32/Pico系の`setSDA`/`setSCL`かを決める
3. 新しいグローバルインスタンス（`Wire3`など）は足さない（§2-1の問題を広げる）

### 5-3. 注意点
- **プルアップ**: A4/A5には基板上のプルアップが無いはず。外付けか内蔵プルアップの有効化が要る（回路図で要確認）
- **A156**: R75/R76を外していないとCANトランシーバがA4を駆動する。LPI2C1は`MB_MOSI`/`MB_SCK`のI²Cと共有で両立しない
- **A156の`setPins`**: ピンだけでなくペリフェラル（LPI2C0→LPI2C1）も切り替わる。クロック設定、リセット解除、割り込みハンドラ、ターゲットモードが追従するかを確認する
- **`analogRead(A4/A5)`との排他**: 0.8.0で直した「`analogRead()`後に入力バッファを戻す」処理との関係も見る
- **`mcxPinState`**: `KNOWN_INSTANCES`などのインスタンス表への追加
- **判定用マクロ**: `WIRE_HAS_A4A5`のようなものがあれば、A153/N947でスケッチがコンパイル時に分岐できる

### 5-4. 進め方の案
1. A156で5-2の1を実機確認する（`release_check`にジャンパ試験を足す）
2. `setPins`の名前とシグネチャを決め、A156で実装する
3. N236は0.9.0のポートでは入れていない（A4/A5はアナログ入力）。入れるなら`Wire1`の出口をA4/A5に切り替える形になる。C444はボード追加の中で対応する
